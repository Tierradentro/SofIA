SofIA Logística Inteligente

WMS multiempresa para IRE e ICV (bodega física compartida, existencias separadas por empresa).

Estado del proyecto — Iteración I14 (residuales QA V2)

I0–I1 Fundaciones + Auth/RBAC/Auditoría I2 Administración I3 Catálogos y productos I4 Importaciones/Exportaciones I5 OCR I6 Ingresos I7 Pedidos y alistamiento I8 Despachos y cajas I9 Devoluciones PQRS I10 Inventarios por empresa I11 API externa I12 Consultas y tablero del comercial I13 Endurecimiento y cierre de spec I14 Residuales QA V2
  • Backend: NestJS 10 + TypeORM + PostgreSQL 16 (migraciones versionadas, seeds idempotentes).
  • Frontend: Next.js 14 (App Router) + Tailwind. Módulos: dashboard, productos, clientes, comerciales, importaciones, OCR, ingresos, pedidos, despachos, devoluciones, inventarios, tablero del comercial; API externa (X-API-Key + rate limit).
  • I14 (QA V2): RBAC en listados/detalle de pedidos (una API key ya no puede navegar /orders interno — 403); la purga de auditoría (que ya exportaba a CSV antes de borrar y se auto-auditaba) ahora permite listar y descargar el respaldo de salvaguarda desde el módulo de administración (GET /audit/purge y GET /audit/purge/:archivo, con protección contra path traversal); la lista de productos marca con badge Incompleto los que el Generador puede completar (código OE, marca, ubicación). Se mantienen las decisiones: bloqueo de inventario solo En Conteo, guía inline, sin scoping de lectura por empresa.
  • I13 (post-QA): endurecimiento de concurrencia (cierre de caja y alistamiento atómicos con pruebas de carrera reales; cancelación libera solo lo no despachado, con whitelist de estados), seguridad (API keys OCR cifradas AES-256-GCM, secretos obligatorios en producción, rate limit de la API externa parametrizable, login sin canal lateral de tiempo), despacho GLOBAL compartido con consecutivo DES-###### (spec v1.1), API externa según spec §7 (PUT de pedido, created_via, nomenclatura /api/orders, /api/products, /api/dispatch, /api/carrier-guide, /api/box), exports CSV de los 5 listados generales, kardex /movimientos y gestión de /empresas en el frontend.
  • I12 (EP-10): consulta de caja enriquecida con cliente, empresas, documentos (facturas) y fecha (HU-053); filtros de despachos por estado, cliente, empresa, rango de fechas, documento, caja y guía (HU-054); tablero del Comercial (M02): los listados y detalles de pedidos, despachos y PQRS quedan restringidos automáticamente a su comercial (404 en detalles ajenos), con página /tablero de resumen.
  • I9 (M11): casos de devolución PQRS con búsqueda de asociación por producto/caja/factura/despacho (HU-044); factura manual u observación obligatoria sin coincidencia (HU-045/CU-007); motivos del catálogo G01–G40/N01–N18 (HU-047); soportes fotográficos con observación (HU-046) y soporte de respuesta del proveedor; ciclo de corrección (Abierta → Pendiente corrección → Abierta); solución y cierre por Operador; cancelación por Generador en cualquier punto; reingreso manual al inventario como movimiento REINGRESO_DEVOLUCION.
  • Pruebas: 56 unitarias + 133 e2e, todas verdes. Humo de producción superado (8/8).

Cómo ejecutar

  • docker-compose.yml en la raíz levanta PostgreSQL, backend, frontend, nginx y ocr-worker.
  • Backend: backend/ — npm run start:prod (aplica migraciones y seeds al arrancar).
  • Frontend: frontend/ — npm run build && npm start.
